## 1. 한 줄 요약

팀이 매일 만드는 **인증 Gold 데이터(`lh_whatif`)를 읽기만 해서**, KOSPI 시장이 지금 **상승장·횡보장·폭락장** 중 어디에 있는지 판정하고, 그 결과를 **국면 분석용 Gold 테이블(`gold_regime_*`, 별도 Lakehouse `LH_MarketRegime`)** 과 **Power BI 보고서(`RPT_MarketRegime`)** 로 제공합니다.

> 과거 데이터 기반 시장 분석이며 투자 권유·종목 추천·수익 보장이 아닙니다.

## 2. Fabric 기초: 아이콘별 항목 종류와 역할

Fabric 워크스페이스의 항목은 종류마다 아이콘이 다릅니다. 한 줄로 비유하면 **Lakehouse는 창고, 노트북은 작업자, 파이프라인은 작업 순서표, 실험은 실험 노트, 의미 체계 모델은 계산 규칙집, 보고서는 화면**입니다.

### 2.1 이번에 만든 항목 종류

| 아이콘 모양 | 종류 | 하는 일 | 우리 항목 |
|---|---|---|---|
| 노란 폴더 | **폴더** | 워크스페이스 안에서 항목을 묶어 정리합니다. 데이터나 권한에는 영향이 없습니다. | `MarketRegime` |
| 파란 집 모양 | **Lakehouse** | 데이터 창고입니다. **Tables**(Delta 테이블, 표 형태)와 **Files**(JSON·parquet·코드 같은 파일)로 나뉩니다. 모든 데이터는 OneLake에 저장됩니다. | `LH_MarketRegime` |
| Lakehouse 아래 같은 이름의 하위 아이콘 | **SQL 분석 엔드포인트** | Lakehouse를 만들면 자동으로 생깁니다. Tables를 SQL로 **읽기 전용** 조회하는 창구이며, Power BI가 연결하는 입구입니다. | `LH_MarketRegime` (하위) |
| Lakehouse 안의 화살표 붙은 폴더/테이블 | **바로가기(Shortcut)** | 다른 Lakehouse의 데이터를 **복사하지 않고 가리키는 링크**입니다. 원본이 바뀌면 바로 반영됩니다. | `gold_evidence`, `gold_stress_daily` |
| `</>` 모양 | **노트북** | Python(PySpark) 코드를 셀 단위로 실행하는 문서입니다. 데이터 가공, 모델 학습, 결과 저장을 합니다. | `NB_R01`, `NB_R02`, `NB_R03` |
| 초록 파이프 모양 | **데이터 파이프라인** | 여러 작업(노트북 실행, 데이터 복사 등)을 **순서대로 자동 실행**하고 일정을 관리합니다. Azure Data Factory와 같은 엔진입니다. | `PL_MarketRegime_Daily` |
| 플라스크(실험 병) 모양 | **ML 실험** | MLflow 실행 기록 저장소입니다. 학습할 때마다 설정값과 성능 지표가 한 줄씩 쌓여서 실행끼리 비교할 수 있습니다. | `MarketRegime_HMM`, `NB_R02_Train_Regime_HMM` |
| 점 격자 모양 | **의미 체계 모델(Semantic model)** | Power BI용 데이터 모델입니다. 어떤 테이블을 쓰는지, 계산식(측정값, DAX)을 어떻게 정의하는지 담습니다. 예전 이름은 "데이터 세트"입니다. | `SM_MarketRegime` |
| 막대 차트 모양 | **Power BI 보고서** | 의미 체계 모델을 읽어 화면(카드, 차트, 표)으로 보여 줍니다. | `RPT_MarketRegime` |

### 2.2 의미 체계 모델의 연결 방식

| 방식 | 특징 | 우리 선택 |
|---|---|---|
| Import | 데이터를 모델 안에 복사합니다. 새로고침해야 최신이 됩니다. | 아님 |
| DirectQuery | 볼 때마다 원본에 SQL 질의를 보냅니다. 느릴 수 있습니다. | 아님 |
| **Direct Lake** | OneLake의 Delta 테이블을 **복사 없이 바로** 읽습니다. 빠르고, 파이프라인이 테이블을 갱신하면 보고서도 바로 최신이 됩니다. | **선택** |

### 2.3 팀 워크스페이스의 다른 항목 종류 (참고)

| 아이콘 | 종류 | 팀 항목 예 | 시장 국면과의 관계 |
|---|---|---|---|
| 복사 아이콘 | 복사 작업(Copy job) | `CopyJob_1~4` | 연결 안 함 |
| 번개 모양 | Eventstream (실시간 스트림 수신) | `es_whatif_quote` | 연결 안 함 (4.3 참고) |
| 데이터베이스 모양 | Eventhouse / KQL 데이터베이스 (실시간 데이터 저장·분석) | `eventhouse_whatif` | 연결 안 함 |

### 2.4 데이터 계층 (메달리온 구조)

| 계층 | 뜻 | 팀 프로젝트에서 |
|---|---|---|
| Bronze | 원천에서 받은 그대로의 데이터 | `lh_whatif/Files/bronze` (API 원본 JSON) |
| Silver | 정제·표준화한 데이터 | `silver_*_daily` Delta 테이블 |
| Gold | 서비스에 바로 쓰는 최종 데이터 | `gold_stress_daily` + 인증 스냅샷 |
| Gold (분석) | 팀 Gold를 입력으로 만든 분석용 Gold 테이블 | 시장 국면 `gold_regime_*` (LH_MarketRegime), 스트레스엔진 결과 (LH_StressLab_ML) |

시장 국면 파트는 **원천 데이터용 Bronze·Silver를 새로 만들지 않고**, 팀 Gold를 입력으로 받아 **국면 분석용 Gold 테이블(`gold_regime_*`)을 직접 만듭니다.** 같은 원천을 두 번 수집하면 데이터 버전이 둘로 갈라지므로, 수집·정제는 팀 파이프라인 하나로 두고 그 위에 분석 Gold를 얹는 구조입니다.

## 3. 폴더 `MarketRegime` 구성 (항목 10개)

| 항목 | 종류 | 역할 |
|---|---|---|
| `LH_MarketRegime` | Lakehouse (+ SQL 분석 엔드포인트) | 국면 분석 결과 전용 저장소. 팀 Gold는 읽기 전용 바로가기로 연결 |
| `NB_R01_Build_Regime_Features` | 노트북 | 1단계: Gold → 시장 상태 피처 생성 |
| `NB_R02_Train_Regime_HMM` | 노트북 | 2단계: HMM 학습, 날짜별 국면 판정, 검증 |
| `NB_R03_Publish_Regime_Snapshot` | 노트북 | 3단계: 결과 게시 (테이블, 스냅샷 JSON, 상태 파일) |
| `PL_MarketRegime_Daily` | 데이터 파이프라인 | R01 → R02 → R03을 순서대로 실행 |
| `MarketRegime_HMM` | MLflow 실험 | 학습 기록 (검증 지표, 설정) |
| `NB_R02_Train_Regime_HMM` | MLflow 실험 | R02 실행 시 Fabric이 노트북 이름으로 자동 생성한 기록 |
| `SM_MarketRegime` | 의미 체계 모델 (Direct Lake) | 보고서용 데이터 모델 (테이블 8개 + 측정값) |
| `RPT_MarketRegime` | Power BI 보고서 | 4페이지 시각화: 개요 / 국면 이력 / 유사 시기 / 모델·데이터 |

이름 규칙은 `LH_`(Lakehouse), `NB_`(노트북), `PL_`(파이프라인), `SM_`(의미 체계 모델), `RPT_`(보고서) 접두사입니다. `R01~R03`은 시장 국면(Regime) 파트의 실행 순서입니다.

기존 팀 항목(`NB_WebAPI` 폴더, `lh_whatif`, 팀 파이프라인 등)은 **하나도 수정하지 않았습니다.** 새 항목만 추가했습니다.

## 4. 팀 데이터와의 연결

### 4.1 연결한 것 (읽기 전용)

`LH_MarketRegime` 안에 **OneLake 바로가기 2개**를 만들어 팀 데이터를 **복사 없이 직접** 읽습니다. 바로가기는 링크일 뿐이라 팀 데이터는 그대로이고, 팀 Gold가 갱신되면 자동으로 최신 데이터를 읽습니다.

| 바로가기 (LH_MarketRegime) | 가리키는 곳 (lh_whatif) | 쓰는 방식 |
|---|---|---|
| `Files/gold_evidence` | `Files/gold_evidence` | **기본 입력.** 인증 Gold 스냅샷 `gold_stock_market_daily_v11/` |
| `Tables/gold_stress_daily` | `Tables/gold_stress_daily` | 예비 입력 (인증 스냅샷을 쓰지 않도록 설정했을 때만) |

인증 Gold 스냅샷에서 읽는 파일은 다음과 같습니다.

| 파일 | 용도 |
|---|---|
| `health.json` | Gold 상태. **ready가 아니면 분석을 시작하지 않음** |
| `latest.json` | 최신 Gold 버전과 위치 |
| `<버전>/certificate.json` | sha256 해시. 파일이 인증받은 그대로인지 확인 |
| `<버전>/gold.parquet` | `gold_stress_daily` v1.1 본문 (20종목 + KOSPI + 거시 지표) |
| `<버전>/input_eligibility.parquet` | 행별 사용 가능 여부. 인증서가 정한 순서대로 적용 |

Gold에 들어 있는 원천 데이터는 다음과 같습니다(팀 수집 파이프라인이 담당).

| 원천 | 내용 | 국면 분석에서 쓰는 곳 |
|---|---|---|
| KRX 공식 API | 20종목 일별 종가·거래량, KOSPI 지수 | 수익률, 변동성, 하락 종목 비율, 종목 간 상관 |
| FRED / ECOS | 원/달러 환율, 미국 10년물, WTI, VIX, 국고채 3년 | 환율·금리·유가 변화, 공포지수 |

### 4.2 팀 데이터 흐름 속 위치

```
[팀 담당]
pl_ingest_official20 (매일 08:00·12:00)
   → Bronze (lh_whatif/Files/bronze)
   → PI_batch_bronze to gold (nb_01_Bronze_to_Silver → nb_03_Gold_Build)
   → Gold: gold_stress_daily + 인증 스냅샷 (lh_whatif)
            │
            │  OneLake 바로가기 (읽기 전용)
            ▼
[시장 국면 파트]
PL_MarketRegime_Daily: NB_R01 → NB_R02 → NB_R03
   → LH_MarketRegime (gold_regime_* 테이블, Files/regime/)
   → SM_MarketRegime (Direct Lake) → RPT_MarketRegime (Power BI)
   → (예정) PostgreSQL regime 스키마 → API → 웹 대시보드 메뉴
```

스트레스엔진ML도 같은 Gold를 읽고 결과를 자기 Lakehouse(`LH_StressLab_ML`)에 따로 저장합니다. 시장 국면 파트도 같은 구조입니다.

### 4.3 연결하지 않은 것과 이유

| 팀 항목 | 연결 여부 | 이유 |
|---|---|---|
| 실시간 시세 (키움 → Event Hubs → `es_whatif_quote` → `eventhouse_whatif`, `pl_realtime_*`) | **연결 안 함** | 국면은 20일·60일 단위 흐름으로 판정하는 **일 단위** 개념입니다. 장중 틱이 바뀌어도 그날의 국면은 바뀌지 않습니다. 또한 실시간 데이터는 인증 Gold에 포함되지 않아 검증된 입력으로 쓸 수 없습니다. |
| `LH_StressLab_ML`, `NB_WebAPI` 폴더 | 연결 안 함 | 스트레스엔진 파트의 영역이며, 입력(Gold)만 공유합니다. |
| `CopyJob_1~4`, PostgreSQL | 아직 안 함 | PostgreSQL 복사와 API 연결은 다음 단계입니다(10장 참고). |

## 5. 항목별 상세

### 5.1 `LH_MarketRegime` (결과 저장소)

**테이블 10개** (2026-11-24 시험 실행 기준 행 수)

| 테이블 | 행 수 | 내용 | 만드는 노트북 |
|---|---|---|---|
| `gold_regime_features` | 6,627 | 날짜별 시장 상태 지표 (수익률, 변동성, 낙폭, 하락 종목 비율, 상관, VIX, 환율·금리·유가 변화 등) | R01 |
| `gold_regime_daily` | 3,802 | 날짜별 국면 확률(상승·횡보·폭락)과 최종 국면 | R02 |
| `gold_regime_runs` | 58 | 국면 구간 (시작일, 종료일, 일수, 구간 중 KOSPI 변화) | R03 |
| `gold_regime_summary` | 3 | 국면별 요약 (일수 비중, 평균 지속일, 연환산 수익률·변동성, 평균 VIX) | R03 |
| `gold_regime_transition` | 9 | 국면 전환 행렬 (3×3) | R03 |
| `gold_regime_similar` | 5 | 현재와 비슷한 과거 시기 Top 5 (KNN) | R03 |
| `gold_regime_current` | 1 | 현재 상태 한 줄 (보고서 카드용) | R03 |
| `gold_regime_validation` | 15 | 검증 지표 (보고서용) | R03 |
| `regime_pg_snapshot` | 1 | PostgreSQL 복사 대기분 (스냅샷 JSON) | R03 |
| `regime_pg_daily` | 3,802 | PostgreSQL 복사 대기분 (날짜별 국면) | R03 |

피처는 Gold 전체 거래일에 대해 만들고, 국면 판정은 필요한 지표가 모두 갖춰진 날부터 합니다. 그래서 두 테이블의 행 수가 다릅니다.

**Files 구조**

```
Files/
├─ gold_evidence/        ← 바로가기 (팀 lh_whatif, 읽기 전용)
├─ reference/market_regime/v1/
│    hmm_numpy.py, regime_core.py, fabric_io.py, manifest.json   ← 모델 코드 (해시 고정)
└─ regime/
     ├─ runs/<RUN_ID>/  context.json, model.json, bic.json, validation.json
     ├─ snapshots/<버전>/  regime_snapshot.json, certificate.json
     ├─ latest.json     ← 최신 스냅샷 위치 + sha256
     └─ health.json     ← ready / blocked
```

| 파일 | 내용 |
|---|---|
| `context.json` | 이번 실행의 설정값, 사용한 Gold 버전 (R01 → R02·R03 전달용) |
| `model.json` | 학습된 HMM의 상태별 평균, 전환 확률, 국면 이름 매핑 |
| `bic.json` | 국면 수 2/3/4의 BIC 비교 결과 |
| `validation.json` | 검증 지표 전체 (7장) |
| `regime_snapshot.json` | API·웹 대시보드가 읽는 최종 결과 묶음 (약 380KB) |
| `certificate.json` | 스냅샷의 sha256, 버전, Gold 버전, 코드 버전 |

현재 최신 스냅샷은 `20261124T120702Z`, 기준일은 `2026-11-23`입니다.

### 5.2 노트북 3개

| 노트북 | 입력 | 처리 | 출력 |
|---|---|---|---|
| **NB_R01** 피처 | 인증 Gold | 전체 거래일 달력에서 수익률·이동창 계산 → 행별 사용 가능 여부 적용 → 사용 가능 종목이 10개 미만인 날은 비움 | `gold_regime_features`, `context.json` |
| **NB_R02** 학습·판정 | 피처 | 국면 수 비교(BIC 2/3/4) → walk-forward HMM → 국면 이름 붙이기 → 5일 확인 규칙 → 검증 (GMM 비교, KNN 일치율 포함) | `gold_regime_daily`, `model.json`, `bic.json`, `validation.json`, MLflow 기록 |
| **NB_R03** 게시 | R01·R02 결과 | 유사 시기(KNN) 계산 → 게시 전 검사 → 스냅샷 JSON + 인증서 → 분석 테이블 → 보고서용 테이블 → PostgreSQL 대기 테이블 → 마지막에 latest/health 교체 | 위 테이블 8개, `Files/regime/` |

**노트북 매개변수** (파이프라인이나 수동 실행 때 바꿀 수 있는 값)

## 6. 모델 설명: HMM · GMM · KNN

### 6.1 세 모델 한눈에 보기

| 약어 | 전체 이름 | 한국어 | 이 프로젝트에서의 역할 | 결과물에 쓰이는 곳 |
|---|---|---|---|---|
| **HMM** | Hidden Markov Model (Gaussian HMM) | 은닉 마르코프 모델 | **주 모델.** 날짜별 국면(상승·횡보·폭락)과 그 확률을 판정 | 현재 국면, 국면 이력, 확률 추이, 전환 행렬 등 **서비스 결과 전부** |
| **GMM** | Gaussian Mixture Model | 가우시안 혼합 모델 | **비교 기준선.** 시간 순서를 무시하고 군집만 나눴을 때와 비교 | 검증 지표(실루엣)에만 |
| **KNN** | K-Nearest Neighbors | K-최근접 이웃 | **보조 분석.** 현재와 시장 상태가 가장 비슷한 과거 날짜 검색 + HMM 판정 교차 확인 | 유사 시기 Top 5, KNN 일치율 |

### 6.2 HMM (Hidden Markov Model, 은닉 마르코프 모델)

**개념.** 시장의 "국면"은 직접 관측할 수 없는 **숨은 상태(hidden state)** 이고, 우리가 보는 수익률·변동성·VIX 같은 지표는 그 상태가 만들어 낸 **관측값**이라고 가정합니다. 모델은 두 가지를 학습합니다.
- **상태별 관측 분포:** 각 국면에서 지표들이 보통 어떤 값을 갖는지 (정규분포의 평균과 분산)
- **전환 확률:** 오늘 국면이 A일 때 내일 국면이 B일 확률 (마르코프 성질: 내일은 오늘 상태에만 의존)

그래서 HMM은 "오늘 지표"만 보지 않고 "어제까지의 흐름"도 함께 반영합니다. 하루 이틀 튀는 값에 국면이 쉽게 흔들리지 않는 것이 GMM과의 가장 큰 차이입니다.

| 설정 | 값 | 이유 |
|---|---|---|
| 국면 수 | 3 | BIC로 2/3/4를 비교한 결과 + 해석 가능성 |
| 분포 | 가우시안, 대각 공분산 | 지표 수 대비 데이터 양을 고려해 과적합 방지 |
| 학습 방법 | EM(Baum-Welch) 알고리즘, 초기값 4회(k-means++)로 시작해 가장 좋은 결과 선택 | 국소 최적해 회피 |
| 전환 확률 사전값 | 디리클레 사전 10 | 국면이 너무 자주 바뀌지 않도록 "머무름"을 조금 선호 |
| 판정 방식 | **필터링 확률** (그날까지의 데이터로만 계산) | 미래 정보 사용 방지. 평활 확률(전체 기간 사용)은 검증 비교용으로만 사용 |
| 학습 방식 | **walk-forward:** 처음 750거래일로 학습을 시작하고 21거래일마다 재학습 | 실제 운영처럼 과거 데이터만으로 판정 |
| 이상치 처리 | 표준화 값 ±4로 제한 | 극단값 하나가 상태를 왜곡하지 않도록 |
| 국면 이름 | 상태별 평균 "추세 − 변동성" 점수 순서로 상승장 / 횡보장 / 폭락장 | 상태 번호(0,1,2)를 사람이 읽을 이름으로 변환 |
| 깜빡임 방지 | 새 국면 확률이 0.6 이상인 날이 5일 연속일 때만 라벨 변경 | 하루짜리 신호로 국면이 바뀌는 것 방지 |

**HMM 입력 지표 6개**

| 지표 | 뜻 |
|---|---|
| `kospi_ret_20d` | KOSPI 20거래일 수익률 (추세) |
| `kospi_vol_20d_log` | KOSPI 20일 변동성 (로그) (흔들림) |
| `breadth_down_5d` | 최근 5일 평균 하락 종목 비율 (하락의 폭넓음) |
| `avg_corr_60d` | 20종목 간 60일 평균 상관 (위기 때 같이 움직이는 정도) |
| `vix_log` | VIX 공포지수 (로그) (글로벌 위험 심리) |
| `usdkrw_chg_20d` | 원/달러 20일 변화 (외국인 자금 압력) |

### 6.3 GMM (Gaussian Mixture Model, 가우시안 혼합 모델)

- 각 날짜를 **서로 독립인 점**으로 보고, 지표 공간에서 3개 군집으로 나눕니다. 시간 순서와 전환 확률이 없습니다.
- 이 프로젝트에서는 "시간 흐름을 반영하는 HMM이 단순 군집보다 의미가 있는가"를 보여 주는 **비교 기준선**으로만 씁니다.
- 실루엣 점수는 GMM이 더 높게 나옵니다(0.18 vs 0.10). 이는 실루엣이 시간 순서를 보지 않는 지표라 GMM에 유리하기 때문입니다. GMM은 날마다 국면이 바뀌어도 감점이 없지만, 시장 국면 분석에는 그런 결과를 쓸 수 없습니다. 그래서 국면 판정에는 HMM을 씁니다.

### 6.4 KNN (K-Nearest Neighbors, K-최근접 이웃)

- **학습 과정이 없는 방법**입니다. 오늘의 지표 11개를 표준화한 뒤, 과거 날짜 중 거리(유클리드)가 가장 가까운 5개(K=5)를 찾습니다.
- 규칙: 최근 60일은 제외하고(자기 자신과 바로 옆 날짜 방지), 결과끼리 최소 30일 간격을 둡니다. **미래 수익률은 쓰지도 보여 주지도 않습니다.**
- 쓰임: ① 보고서·웹의 "유사 시기" ② HMM 검증. 비슷한 날들이 HMM에서도 같은 국면으로 판정됐는지 확인합니다(KNN 일치율).

**KNN 입력 지표 11개:** KOSPI 20일 수익률, 20일 변동성(로그), 1년 고점 대비 낙폭, 5일 하락 종목 비율, 60일 평균 상관, 20일 종목 간 분산, VIX(로그), 원/달러 20일 변화, 미국 10년물 20일 변화, 국고채 3년 20일 변화, WTI 20일 변화. 그날 값이 비어 있는 지표는 빼고 계산하며, 뺀 지표는 스냅샷에 기록합니다.

### 6.5 왜 파일 이름에 HMM만 있나요?

1. **서비스 결과를 만드는 모델이 HMM 하나이기 때문입니다.** 현재 국면, 국면 이력, 확률, 전환 행렬은 모두 HMM의 출력입니다. 모델 버전도 `regime-hmm-v1`입니다.
2. **"학습(Train)"하는 모델이 HMM뿐입니다.** `NB_R02_Train_Regime_HMM`은 학습 노트북이라 학습 대상의 이름이 붙었습니다. KNN은 학습 단계가 없는 검색 방법이고, GMM은 검증 안에서 비교용으로 잠깐 맞춰 볼 뿐 결과를 저장하지 않습니다.
3. **KNN과 GMM도 실제로 실행됩니다.** GMM과 KNN 일치율은 NB_R02의 검증 단계에서, 유사 시기(KNN)는 NB_R03 게시 단계에서 계산됩니다. 결과는 `validation.json`, `gold_regime_validation`, `gold_regime_similar`에 들어 있습니다.
4. MLflow 실험 `MarketRegime_HMM`도 같은 이유로, 기록하는 대상이 HMM 학습 실행이라 이 이름을 붙였습니다.
5. 처음 계획에 있던 Copula(위기 시나리오 생성)는 "시장 분석만 한다"는 범위 결정에 따라 제외했습니다.

## 7. 성능 지표의 뜻

| 지표 | 계산 방법 | 읽는 법 | 이번 값 |
|---|---|---|---|
| **BIC** (Bayesian Information Criterion, 베이즈 정보 기준) | 모델 적합도에 복잡도 벌점을 더한 값 | 낮을수록 좋음. 국면 수 2/3/4를 고를 때 사용 | `bic.json` 참고, 3개 채택 |
| **표본외 일수** | 학습에 쓰지 않은 기간(walk-forward)으로 판정한 거래일 수 | 길수록 평가를 믿을 수 있음 (게시 최소 기준 252일) | 3,052일 |
| **사건 포착률** (`bear_share`) | 알려진 하락 사건 기간 중 폭락장으로 판정된 날의 비율 | 1.00이면 기간 전체를 폭락장으로 판정 | 코로나 1.00 / 2022 0.27 / 2024.8 0.14 / 2025.4 0.13 |
| **평균 폭락 확률** (`mean_p_bear`) | 사건 기간 동안 폭락장 확률의 평균 | 라벨이 늦게 바뀌어도 확률이 올랐는지 확인 | 1.00 / 0.31 / 0.71 / 0.63 |
| **연간 국면 전환 횟수** | 1년 동안 라벨이 바뀐 횟수 | 너무 적으면 둔하고, 너무 많으면 불안정. 내부 기준 2~8회 | 3.8회 |
| **필터-평활 일치율** | 그날까지의 데이터로 한 판정(필터)과 전체 기간으로 한 사후 판정(평활)이 같은 날의 비율 | 높을수록 실시간 판정이 나중에 뒤집히지 않음 | 96.3% |
| **KNN 국면 일치율** | 비슷한 과거 날짜(KNN)가 HMM에서도 같은 국면이었던 비율 | **무작위 기준보다 높아야** 국면 구분이 지표와 일관됨 | 62.0% |
| **무작위 기준** | 국면 비중만 맞춰 무작위로 골랐을 때 기대되는 일치율 | KNN 일치율의 비교 대상 | 38.1% |
| **실루엣** (Silhouette) | 같은 군집끼리는 가깝고 다른 군집과는 먼 정도 (-1~1) | 시간 순서를 보지 않아 GMM에 유리. **보조 근거로만** 사용 | HMM 0.10 / GMM 0.18 |

정답 라벨이 없는 비지도 모델이라 "정확도" 같은 단일 점수가 없습니다. 그래서 **알려진 사건을 잡는지, 안정적인지, 나중에 뒤집히지 않는지, 다른 방법과 일관된지**를 함께 봅니다.

## 9. 알려진 한계 (발표 때 설명할 것)

1. **국면 이름과 실제 수익률이 어긋남.** 상승장의 연환산 수익률이 -6.98%, 폭락장이 +16.86%입니다. 모델이 국면을 사실상 **변동성 크기**로 나누고 있기 때문입니다. 2026년처럼 지수가 크게 오르면서 크게 흔들린 기간도 "폭락장"으로 분류됩니다. → 이름을 **저변동 / 중변동 / 고변동(위기)** 으로 바꾸는 방안을 검토 중입니다.
2. **완만한 하락장은 잘 못 잡음.** 2022년처럼 변동성이 낮은 채로 천천히 빠지는 하락은 횡보장으로 분류되는 경향이 있습니다.
3. **단기 급락은 라벨 반영이 늦음.** 확률은 바로 오르지만 5일 확인 규칙 때문에 라벨 전환이 늦습니다. 깜빡임을 막기 위해 일부러 택한 방식입니다.
4. **일 단위 분석.** 장중 실시간 변화는 반영하지 않습니다(4.3 참고).
5. **입력 범위.** 팀 Gold에 있는 20종목과 거시 지표 6종만 씁니다. 업종 지수, 외국인 수급, 신용 스프레드 등은 Gold에 없어 쓰지 않았습니다.

**멈췄을 때 메시지별 의미**

| 메시지 | 의미 | 조치 |
|---|---|---|
| `GOLD_NOT_READY` | 팀 Gold가 갱신 중이거나 인증 해시가 맞지 않음 | 팀 Gold 파이프라인이 끝난 뒤 다시 실행. 데이터는 손상되지 않음 |

| `TEAM_LAKEHOUSE_DETECTED` | 노트북 기본 Lakehouse가 `lh_whatif`로 잡힘 | 기본 Lakehouse를 `LH_MarketRegime`으로 변경 |
| `AS_OF_NOT_GOLD_LATEST` | 국면 기준일이 Gold 최신일과 다름 | Gold 재실행 여부 확인 후 R01부터 다시 실행 |
| `OUT_OF_SAMPLE_TOO_SHORT`, `HISTORY_TOO_SHORT` | 이력이 짧음 | Gold 기간 확인 |
| `CURRENT_PROBABILITIES_INVALID` | 확률 합 오류 | R02 출력 확인 |
| `NOT_FABRIC_GOLD_DATA` | 실제 Gold가 아닌 데이터 | `DATA_MODE` 매개변수 확인 |

| Delta 테이블 | parquet 파일 + 변경 기록으로 된 테이블 형식. 버전 관리와 안전한 덮어쓰기 지원 |
| parquet | 열 단위로 압축 저장하는 데이터 파일 형식 |
| 스냅샷 | 특정 시점의 결과를 통째로 묶어 고정한 파일. 이후 변하지 않음 |
| sha256 해시 | 파일 내용의 지문. 한 글자만 바뀌어도 값이 달라져 변조·손상 확인에 사용 |
| walk-forward | 과거 데이터로 학습하고 그다음 기간을 판정하는 일을 시간 순서대로 반복하는 평가 방식 |
| 표본외(Out-of-sample) | 학습에 쓰지 않은 데이터로 평가한 구간 |
| 필터링 / 평활 확률 | 그날까지의 데이터만 쓴 확률 / 전체 기간을 다 쓴 사후 확률 |
| 측정값(DAX) | Power BI 의미 체계 모델의 계산식 |
| ETag / 304 | 데이터가 바뀌지 않았으면 다시 받지 않게 하는 웹 캐시 방식 |

## 13. 예상 질문과 답

**Q. 팀 데이터를 복사했나요? 팀 데이터가 바뀔 위험은 없나요?**
A. 복사하지 않았습니다. 바로가기로 읽기만 하고, 결과는 별도 Lakehouse에만 씁니다. 노트북이 `lh_whatif`에 쓰려고 하면 스스로 멈추게 해 두었습니다. 구축 전후로 팀 항목과 `lh_whatif` 파일을 비교해 변화가 없음을 확인했습니다.

**Q. 실시간 데이터는 왜 안 쓰나요?**
A. 국면은 20일·60일 단위의 흐름이라 장중 틱으로는 바뀌지 않습니다. 그리고 검증된 인증 Gold만 입력으로 쓰는 것이 원칙입니다. 실시간 정보는 스트레스 테스트와 시장 상태 API가 담당합니다.

**Q. 스트레스엔진ML과 무엇이 다른가요?**
A. 같은 Gold를 입력으로 공유합니다. 스트레스엔진은 충격이 주어졌을 때 포트폴리오에 미치는 영향을 계산하고, 시장 국면은 지금 시장이 어떤 상태인지를 설명합니다. 결과 저장소도 각자 따로입니다(`LH_StressLab_ML` / `LH_MarketRegime`).

**Q. 미래를 예측하나요?**
A. 아닙니다. 그날까지의 데이터로 현재 상태를 판정하는 분석입니다. 유사 시기도 과거의 비슷한 날짜만 보여 주고, 그 이후 수익률은 일부러 표시하지 않습니다.

**Q. 왜 폭락장인데 수익률이 플러스인가요?**
A. 9장 1번과 같습니다. 모델이 변동성 중심으로 국면을 나누기 때문이며, 이름 기준을 조정할 예정입니다.

**Q. 왜 파일 이름에 HMM만 있고 GMM·KNN은 없나요?**
A. 국면 판정 결과를 만드는 학습 모델이 HMM 하나이기 때문입니다. KNN은 학습이 없는 유사 시기 검색이고, GMM은 비교용 기준선입니다. 둘 다 노트북 안에서 실행되며 결과는 검증 지표와 유사 시기 테이블에 들어 있습니다(6.5).

**Q. GMM이 실루엣 점수가 더 높은데 왜 HMM을 쓰나요?**
A. 실루엣은 시간 순서를 보지 않아, 날마다 국면이 바뀌는 결과에도 감점이 없습니다. 시장 국면은 며칠~몇 달 이어지는 흐름이어야 의미가 있으므로, 전환 확률로 지속성을 반영하는 HMM을 씁니다(6.3).

**Q. Power BI 보고서와 웹 대시보드는 뭐가 다른가요?**
A. 같은 결과를 보여 주는 두 개의 창입니다. Power BI는 팀 내부 검토·발표용으로 지금 바로 볼 수 있고, 웹 대시보드는 서비스 사용자용으로 PostgreSQL·API 연결 후 실데이터가 표시됩니다(5.6).

**Q. 매일 자동으로 도나요?**
A. 일정은 만들어 두었지만 꺼져 있습니다. 팀 Gold 갱신 시각과 맞춰 켤 예정입니다.

## 부록 A. 팀 Gold를 어떻게 쓰나: 파생 Gold와 데이터 적합성

### A.1 파생 Gold란

`gold_regime_*` 테이블은 **팀 Gold를 입력으로 만든 파생(분석용) Gold**입니다. 원천 수집과 정제(Bronze·Silver·Gold)는 팀 파이프라인 하나로 두고, 시장 국면 파트는 그 결과 위에 국면 분석 계층을 얹었습니다. 스트레스엔진(`LH_StressLab_ML`)도 같은 방식입니다.

팀 Gold를 100% 다 쓰는 것은 아닙니다. `gold_stress_daily` 34개 열 중 **국면 분석에 필요한 열만 골라 씁니다.**

### A.2 사용하는 열과 사용하지 않는 열

**사용하는 열**

| 열 | 용도 |
|---|---|
| `trading_date`, `asset_id` | 날짜·종목 기준 (중복이 있으면 정지) |
| `close` | 20종목 종가 → 하락 종목 비율, 종목 간 상관, 종목 간 분산 |
| `volume` | 거래량 지표(`volume_z_60d`). 피처 테이블에만 있고 HMM·KNN 모델에는 넣지 않음 |
| `kospi_close` | KOSPI 수익률, 변동성, 1년 고점 대비 낙폭 (**가장 중요한 입력**) |
| `usdkrw`, `us_treasury_10y`, `wti`, `vix`, `korea_3y` | 환율·금리·유가 변화, 공포지수 |
| `price_basis` | 수정주가(`adjusted`) 행만 사용 |
| `is_mock` | 모의 데이터 행 제외 |
| `input_eligible` (인증 스냅샷의 `input_eligibility.parquet`) | 행별 사용 가능 여부. 인증서가 정한 순서대로 적용 |
| `quality_status` | 예비 경로(인증 스냅샷을 쓰지 않을 때)에서 `valid` 행만 사용 |

**사용하지 않는 열**

| 열 | 쓰지 않는 이유 |
|---|---|
| `sector_id`, `instrument_kind` | 국면 분석은 시장 전체 단위라 업종·상품 구분이 필요 없음 |
| `*_observation_date`, `*_observed_at`, `*_available_at`, `price_available_at` | 시각 정렬(언제 알 수 있었던 값인지)은 팀 Gold 단계에서 이미 처리됨. 그 결과만 사용 |
| `adjustment_version`, `source_ref`, `dataset_version` | 출처·버전 추적용. 대신 Gold 인증 버전과 해시를 결과 스냅샷에 기록 |

### A.3 국면 분석과 잘 맞는 부분

| 국면 분석에 필요한 것 | 팀 Gold에 있나 |
|---|---|
| KOSPI 일별 종가 (추세, 변동성, 낙폭) | 있음. 가장 중요한 입력 |
| 글로벌 위험 심리(VIX), 환율, 금리, 유가 | 있음 (FRED·ECOS 5종) |
| 데이터 품질 관리 (해시 인증, 행별 사용 가능 여부, 시각 정렬, 모의 데이터 표시) | 있음. 일반적인 프로젝트보다 엄격함 |
| 충분한 기간 | 있음. 표본외 판정만 3,052거래일 |

실제 Gold로 실행해 코로나19 급락을 100% 잡았고, 국면 전환 빈도도 안정적이었습니다. 국면 분석에 쓸 수 없는 데이터는 아니라는 뜻입니다.

### A.4 안 맞거나 약한 부분

팀 Gold는 **스트레스엔진 목적에 맞춰 수집**된 데이터라서 국면 분석에는 아래 한계가 있습니다.

| 한계 | 영향 | 대응 |
|---|---|---|
| **종목이 20개뿐** (스트레스 테스트용 대형주 중심) | "하락 종목 비율"과 "종목 간 상관"이 KOSPI 전체(약 900종목)가 아니라 주요 20종목 기준입니다. 삼성전자·SK하이닉스의 영향이 큽니다. | 한계로 명시하고, 화면·문서에 "주요 20종목 기준"으로 표기 |
| **한국 고유 위험 지표가 없음** (VKOSPI, 외국인·기관 수급, 신용 스프레드 등) | 한국 시장의 공포 수준을 미국 VIX로 대신 봅니다. 2022년처럼 한국 고유 요인으로 천천히 빠진 하락을 약하게 잡은 이유 중 하나일 수 있습니다. | 팀 수집 파이프라인에 추가되어야 가능 (팀 결정 사항) |
| **사용 가능 여부 기준이 스트레스엔진 기준** | 스트레스 계산에 맞춰 제외된 행이 국면 분석에서도 빠집니다. 사용 가능 종목이 10개 미만인 날은 피처를 비웁니다. | 현재는 문제 없음. 제외된 날 수는 스냅샷의 `quality`에 기록 |
| **Gold 구조 변경에 영향을 받음** | 스트레스엔진 쪽 사정으로 Gold 버전(v1.1)이나 열 이름이 바뀌면 NB_R01이 멈출 수 있습니다. | 인증 확인 덕분에 **잘못된 결과가 게시되지는 않음**. Gold 변경 시 미리 공유해 달라고 팀에 요청 |
| **일 단위 데이터** | 장중 변화는 반영되지 않습니다. | 부록 B 참고 |

"폭락장인데 수익률이 플러스" 문제(9장 1번)는 데이터가 아니라 **국면 이름을 붙이는 방식(모델 쪽)** 의 문제라서 이 표와는 별개입니다.

### A.5 발표용 한 문장

> 스트레스엔진과 같은 인증 Gold를 공유해 데이터 일관성을 지켰고, 그 대가로 주요 20종목 기준이라는 범위의 한계가 있습니다. VKOSPI와 수급 데이터가 추가되면 개선할 수 있습니다.

## 부록 B. 실시간 데이터(Eventstream·Eventhouse)를 연결하지 않아도 괜찮은가

**결론: 괜찮습니다. 의도한 설계입니다.**

### B.1 팀 데이터 경로는 두 갈래입니다

```
① 일별 공식 데이터 경로 (배치)                  ← 시장 국면이 쓰는 경로
   KRX 공식 API · FRED · ECOS
   → pl_ingest_official20 (매일 08:00·12:00)
   → Bronze → Silver → Gold (PI_batch_bronze to gold)
   → Gold 인증 스냅샷 (lh_whatif/Files/gold_evidence)
   → [시장 국면] LH_MarketRegime

② 실시간 시세 경로 (스트림)                      ← 시장 국면은 쓰지 않음
   키움 REST/WSS → 시세 수집기 → Event Hubs
   → es_whatif_quote (Eventstream) → eventhouse_whatif (Eventhouse, KQL)
   → pl_realtime_session (1분 주기) 등 → 장중 시장 상태 API
```

- Bronze → Silver → Gold는 **실시간으로 만들어지는 것이 아니라, 하루 1~2회 도는 일별 배치**입니다. 입력도 실시간 시세가 아니라 **KRX 공식 일별 자료와 FRED·ECOS 거시 지표**입니다.
- 실시간 시세는 Eventstream → Eventhouse에 따로 쌓이고, 장중 시장 상태를 보여 주는 데 쓰입니다.
- 팀의 `nb_realtime_close_handoff`, `pl_realtime_close`는 이름으로 보면 장 마감 종가를 넘겨주는 역할로 보입니다. Gold에 반영되는지는 담당 팀원에게 확인이 필요합니다. 다만 반영되더라도 시장 국면은 **인증된 Gold 스냅샷만** 읽기 때문에, 인증을 통과한 값만 들어옵니다.

### B.2 실시간을 연결하지 않은 이유

1. **국면은 일 단위 개념입니다.** 모든 지표가 20일·60일 단위 흐름이라 장중 틱이 바뀌어도 그날의 국면은 거의 바뀌지 않습니다.
2. **모델이 일별 종가로 학습됐습니다.** 장중 가격을 섞으면 학습 때와 다른 성격의 데이터가 들어가 판정이 흔들립니다.
3. **장 중간 값은 확정값이 아닙니다.** 오전 급락 후 오후에 회복하면 국면이 하루에도 몇 번씩 뒤집힐 수 있고, 사용자에게 혼란만 줍니다.
4. **검증된 입력 원칙.** 실시간 데이터는 인증(해시, 사용 가능 여부) 과정을 거치지 않습니다.
5. **역할 분담.** 장중 상태는 팀의 실시간 경로(시장 상태 API)가 이미 담당합니다. 국면 분석이 같은 일을 하면 중복입니다.

### B.3 만약 연결한다면 생기는 문제

| 문제 | 설명 |
|---|---|
| 판정 불안정 | 확정되지 않은 장중 값으로 국면이 자주 바뀜 |
| 비용·부하 | 1분 주기로 HMM 전체를 다시 계산하면 팀 용량을 많이 씀 (현재 1회 약 8분) |
| 팀 항목 의존 증가 | Eventhouse 구조가 바뀌면 국면 분석도 영향을 받음 |
| 재현성 저하 | 같은 날짜라도 실행 시각에 따라 결과가 달라짐 |

### B.4 나중에 실시간과 함께 쓰는 방법 (선택)

모델은 그대로 두고 **화면에서 나란히 보여 주는 방식**을 권장합니다.
- 웹 화면에서 일별 국면 카드 옆에 시장 상태 API의 장중 정보(예: "장중 KOSPI -3% 급변")를 함께 표시합니다.
- 국면 판정은 장 마감 확정 데이터로만 하고, 장중 정보는 "참고"로만 표시합니다.

## 부록 C. 작업물이 바뀌는 시간 주기

### C.1 무엇이 언제 바뀌나

| 대상 | 바뀌는 주기 | 무엇이 계기인가 |
|---|---|---|
| 입력: 팀 Gold 인증 스냅샷 | 팀 일정에 따름 (`pl_ingest_official20` 08:00·12:00 → Gold 배치) | 팀 파이프라인 |
| `PL_MarketRegime_Daily` 실행 | **현재: 수동 실행만** (일정 꺼짐) → 켜면 **하루 1회** (10:30 또는 12:30) | 일정 / 수동 실행 |
| 분석 기준일(`as_of`) | 실행할 때마다 Gold 최신 거래일로. 보통 **직전 거래일 종가 기준** | Gold |
| 국면 확률(상승·횡보·폭락) | 실행할 때마다 (하루 1회) | 새 거래일 데이터 |
| 국면 라벨 | 새 국면 확률이 0.6 이상인 날이 **5거래일 연속**일 때만 바뀜 | 5일 확인 규칙 |
| HMM 모델(상태 평균·전환 확률) | **21거래일마다 재학습** (약 한 달) | walk-forward 규칙 |
| 유사 시기 Top 5 | 실행할 때마다 | 새 거래일 데이터 |
| Power BI 보고서 | 파이프라인이 끝나면 **바로** (Direct Lake가 자동 반영) | 테이블 갱신 |
| PostgreSQL → API → 웹 (예정) | 복사 후 바로. API는 최대 5분 캐시 | 10.3 복사 활동 |
| 장중(실시간) | **바뀌지 않음** | 실시간 미연결 (부록 B) |

- 주말과 휴장일에는 새 거래일이 없으므로 실행해도 기준일과 결과가 같습니다.
- 과거 날짜의 판정은 그날까지의 데이터로만 계산했기 때문에, 새 데이터가 들어와도 바뀌지 않습니다. 팀 Gold의 과거 값 자체가 수정된 경우만 예외입니다.

### C.2 하루 흐름 예시 (일정을 10:30으로 켰을 때)

| 시각 (KST) | 일어나는 일 |
|---|---|
| 08:00 | 팀 공식 데이터 수집 (`pl_ingest_official20`) → Bronze·Silver·Gold 갱신, 인증 스냅샷 발행 |

### C.3 사용자에게 설명할 때

## 부록 D. 국면 이름을 그대로(상승장·횡보장·폭락장) 쓸 때의 설명

### D.1 왜 "폭락장"의 연환산 수익률이 플러스인가

`gold_regime_summary`의 연환산 수익률은 **그 국면으로 판정된 날들의 KOSPI 지수 수익률을 모아 연 단위로 환산한 값**입니다. 투자 전략의 수익률이 아닙니다.

- 이 모델은 국면을 주로 **변동성(흔들림의 크기)** 으로 구분합니다. "폭락장"은 급락이 주로 일어나는 **고변동 국면**입니다.
- 급락 직후에는 큰 폭의 반등도 같은 고변동 국면 안에서 일어납니다. 예를 들어 2020년 코로나 급락 뒤의 급반등, 2026년의 큰 폭 상승과 급락이 모두 이 국면에 들어갑니다.
- 그래서 하루하루의 움직임은 매우 크지만, 급락일과 급반등일을 합친 평균은 플러스가 될 수 있습니다. 변동성이 42.6%로 다른 국면의 2.5~3배라는 점이 이 국면의 핵심 특징입니다.
- 반대로 "상승장"은 변동성이 가장 낮은 차분한 국면입니다. 방향은 약하게 내릴 때도 있어 연환산 수익률이 -6.98%로 나왔습니다.

### D.2 이름의 의미 (발표용)

| 이름 | 실제 성격 | 평균 변동성 | 평균 VIX |
|---|---|---|---|
| 상승장 | 변동성이 낮고 차분한 국면 | 12.64% | 14.30 |
| 횡보장 | 변동성이 보통인 국면 | 17.14% | 18.85 |
| 폭락장 | 변동성이 크게 높아진 위기·격변 국면 (급락과 급반등이 함께 나타남) | 42.60% | 25.13 |

> 국면 이름은 각 국면의 **대표적인 시장 분위기**를 나타냅니다. 방향(오르는지 내리는지)은 국면 이름이 아니라 **국면 구간별 KOSPI 변화율**(국면 이력 페이지)로 따로 확인합니다.

### D.3 예상 질문

**Q. 폭락장인데 수익률이 플러스면, 공매도하면 손해 아닌가요? 이걸로 매매하면 되나요?**
A. 이 수치는 KOSPI 지수 자체의 과거 움직임을 국면별로 묶어 본 것이고, 매매 전략의 성과가 아닙니다. 고변동 국면은 급락과 급반등이 함께 나타나서 같은 국면 안에서도 방향이 크게 바뀝니다. 이 분석은 투자 판단이나 매매 신호가 아니며, 현재 시장이 얼마나 불안정한 상태인지를 설명하는 데 목적이 있습니다.

**Q. 이름을 바꿀 계획은 있나요?**
A. 성격을 더 정확히 드러내도록 저변동·중변동·고변동으로 바꾸는 버전을 준비해 두었습니다. 현재는 이해하기 쉬운 상승장·횡보장·폭락장을 유지하고, 위 설명을 함께 제공합니다.
