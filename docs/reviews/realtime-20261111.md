# 실시간 경로 점검 및 연결 처리 수정

2026-11-11 민철 점검. Functions 연결 처리만 수정했습니다. Fabric 데이터, KQL 함수, 파이프라인, Gold와 ML은 변경하지 않았습니다.

## 1. 전일 종가 갱신

확인된 원인은 자동 갱신 단계 누락입니다. 11월 11일 장중 `previous_close` 20종목의 기준일은 모두 11월 9일입니다. Gold에는 11월 10일 종가가 있습니다.

명령 이력에는 11월 10일 16:37 KST에 `external_table('gold_stress_daily')`를 읽어 `.set-or-replace previous_close`를 실행한 기록이 있습니다. 이후 예약 갱신은 확인되지 않았습니다. Gold 바로가기가 갱신돼도 복사해 둔 `previous_close` 테이블은 자동으로 바뀌지 않습니다.

수정 위치:

1. `pl_ingest_official20`: Gold 검증·게시 성공 뒤 실시간 참조 테이블 갱신 단계를 추가합니다. 거래일 달력으로 정한 직전 거래일, 대상 20종목, 가격의 유효성을 확인한 뒤 게시합니다. 종목마다 제각각 오래된 날짜를 선택하면 안 됩니다.
2. Eventhouse `previous_close`: 현재 시세와 같은 가격 기준의 전일 종가를 저장합니다. 수정주가를 사용할 때에는 현재가와 조정 기준이 일치하는지 확인합니다. 기업행사일에는 검증된 전일 대비 기준가격을 사용합니다.
3. `market_state_v2()`의 `let prevc`: `trade_date`를 버리지 않고 직전 거래일과 대조합니다. 기준일이 다르면 전일 대비 수익률을 정상 수치로 제공하지 않습니다. 현재가와 최근 5분 수익률은 별개입니다.

실제 조회한 같은 삼성전자 현재가 203,750원에서 11월 9일 종가 189,900원을 쓰면 +7.29%, 11월 10일 종가 198,900원을 쓰면 +2.44%입니다. 따라서 표시만의 문제가 아닙니다.

## 2. 원본 틱 중복

11:00~11:30 KST에 `quote_events`는 74,176행, 고유 `event_id`는 37,088개였습니다. 모두 2개씩 저장됐습니다. 전일의 이미 저장된 extent에서도 같은 ID가 두 행으로 존재합니다. 단순 화면 중복이 아닙니다.

같은 시간대 Event Hubs 유입은 37,195건이고, 수집기 로그의 발행 실패는 0건입니다. 원본 수신 시각과 Event Hubs 집계 시각의 경계 차이 때문에 두 수치는 완전히 같지는 않습니다. 확인한 증거는 중복 구간을 Event Hubs 이후 Fabric 적재 쪽으로 좁힙니다. Event Hubs 송신이 약 두 배인 것은 Functions와 Fabric이 각각 소비하는 구조와 일치하므로 그 자체를 중복 원인으로 보지 않습니다.

Eventstream `es_whatif_quote` 정의에는 입력 하나와 `quote_events` 목적지 하나만 있습니다. 원본 테이블 update policy도 비어 있습니다. 따라서 중복 연결이나 특정 담당자의 설정 변경을 원인으로 확정하지 않았습니다. 두 적재 시각은 매우 가깝지만 정밀 시각까지 동일하지는 않습니다.

수정·확인 위치:

1. `es_whatif_quote`의 DirectIngestion 연결과 `quote_events`의 실제 수집 연결을 대조합니다. 다른 연결이 같은 원천을 다시 쓰는지, 내부 재전송인지 확인한 뒤 중복 경로가 확인된 경우에만 정리합니다. 현재 정의만 보고 연결을 삭제하면 안 됩니다.
2. `qe_clean()`의 `summarize take_any(*) by event_id`는 유지합니다. `qe_bars()`가 이를 호출하므로 확인한 분봉 계산은 틱 수와 거래량을 그대로 두 배로 더하지 않습니다. 다른 소비 코드도 원본을 직접 합산하지 않아야 합니다.
3. 원본 행 수 / 고유 이벤트 수 비율을 감시합니다. 같은 ID에서 가격·거래량이 다른 경우에는 단순 중복 제거로 덮지 않고 별도 오류로 분리합니다.

이번에는 Fabric 연결을 변경하거나 원본을 삭제하지 않았습니다. 중복의 세부 원인은 아직 미확정입니다.

## 3. Functions 연결 시간 초과 수정

대상은 저희가 구현한 `services/quote-updater`입니다. 최근 로그에는 `read_latest()`의 PostgreSQL 연결 시간 초과와 PubSub의 300초 응답 대기가 있습니다. DB 또는 네트워크가 최초에 지연된 하위 원인은 로그만으로 확정되지 않았습니다. 다만 코드가 매초 연결을 새로 만들고 긴 대기로 전송을 막는 문제는 확인했습니다.

| 파일 / 함수 | 수정 내용 |
| --- | --- |
| `src/function_app.py` / `read_latest()` | 조회 전용 연결 재사용, 쓰기 연결과 분리, 동시 조회 잠금, 연결 3초·SQL 2.5초 제한, 실패 연결 폐기 후 5초 뒤 재연결 |
| `src/function_app.py` / `latest_snapshot()` | 조회 장애 시 빈 시세를 성공으로 보내지 않고 HTTP 503과 재시도 안내 반환 |
| `src/live_push.py` / `client()` | PubSub 연결 2초·읽기 3초 제한. SDK 내부 재시도 대신 다음 타이머에서 최신 DB 값을 다시 전송 |
| `tests/test_connection_recovery.py` | 연결 재사용, 쓰기 연결 분리, 장애 후 복구, 동시 조회, 503, 실제 SDK 제한 설정 검사 |

전송에 실패한 값을 전송 완료로 표시하지 않는 기존 동작은 유지합니다. 1초 갱신 목표는 정상 상태 기준이며 장애 중 매초 전송을 보장한다는 뜻은 아닙니다.

11:48 KST에 기존 `func-whatif-dev`에 Python 파일 두 개만 교체했습니다. 기존 배포 패키지를 백업했고 나머지 파일과 라이브러리는 바꾸지 않았습니다. 앱 설정, 관리 ID, 네트워크, CORS, 런타임, 스케일 설정은 배포 전후 동일합니다.

로컬 검사: 기존 검사 포함 9개 통과. 모의 장애는 로컬에서만 주입했습니다. 운영 DB나 PubSub를 강제로 끊지 않았습니다.

배포 후 실제 수신 검사(11:48:55~11:52:09 KST):

- 현재가 묶음 184개, 20종목 모두 가격 변화 확인, 관찰 중 이벤트 중복 0건.
- 전송 간격 중앙값 1.000초, 최대 7.996초. 일시적인 공백이 있어 매초 무중단 전달까지 확인했다고 판단하지 않습니다.
- 초기 현재가 조회 4회 모두 HTTP 200, 매회 20종목과 갱신된 체결 시각 반환.
- 기존 시장 분석 스트림도 서로 다른 스냅샷 3개 수신.
- 반영 후 수집된 App Insights 기록: `eh_to_pg` 1,615회, 전송 타이머 232회, 실패 0건. 조회한 예외 및 DB 재연결 경고 0건. 로그 수집 지연과 짧은 관찰 기간이 있으므로 장기간 무장애를 보장하는 결과는 아닙니다.

라이브러리의 연결 재사용·시간 제한 동작은 [Psycopg 연결 설명](https://www.psycopg.org/psycopg3/docs/advanced/async.html)과 [Web PubSub Python SDK](https://learn.microsoft.com/en-us/azure/azure-web-pubsub/reference-server-sdk-python)를 참고했고, 설치된 SDK 객체와 실제 배포 실행으로 확인했습니다.
