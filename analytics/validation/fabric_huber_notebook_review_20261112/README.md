# Fabric ML 노트북을 기존 Huber 계산에 연결하는 수정안

2026-11-12 민철 검토. 현재 Fabric 노트북 14개, 예약 파이프라인 정의와 최근 실행 기록, 게시 스냅샷을 직접 읽었습니다. 노트북 실행, 클라우드 수정, 모델 배포는 하지 않았습니다. 각 원본의 해시와 읽은 시각은 `review_evidence.json`에 있습니다. 아래 줄 번호는 그 시점에 내려받은 `notebook-content.py` 기준입니다.

기존 노트북과 파이프라인을 유지하고, Huber 경로에서 로컬 검증 패키지의 함수를 직접 호출하는 것이 적합합니다. 식을 PySpark나 노트북 셀에서 다시 구현하면 입력과 구간이 달라질 수 있으므로 동일 Python 패키지와 설정을 사용합니다. 현재 CatBoost/Ridge 계산은 해당 모델의 기존 연구 경로로 보존합니다. Huber를 활성화하기 전까지 현재 운영 패키지와 PostgreSQL 게시 포인터를 바꾸지 않습니다.

## 먼저 해결할 피처 갱신 연결

확인한 게시 자료:

- Gold 인증서: `latest_gold_date=2026-11-11`, `latest_eligible_date=2026-11-11`.
- ML 스냅샷: `as_of_trading_date=2026-11-09`, 지원 18종목.
- ML 파이프라인 최근 실행: 11월 12일 08:54 시작, 08:56:37 KST 완료.
- 실행 순서: `NB10_Create_Snapshot → NB11_Prepare_Export → Copy_Market_Features → Copy_Asset_Features → Promote_Verified_Snapshot`.

`NB_10_Scheduled_Stable_Snapshot` 72~73행은 기존 `market_state`와 `asset_features_candidate`를 읽습니다. 이 파이프라인에는 Gold에서 그 두 테이블을 다시 만드는 NB_01이 없습니다. 같은 데이터이면 생성시각을 보존하는 143~150행의 중복 방지 로직은 유지하면 됩니다. 새 날짜의 원천 피처가 만들어지도록 앞단 연결을 보완해야 합니다. 단, 여기서 확인한 것은 Fabric 게시 스냅샷이며 현재 웹이나 PostgreSQL의 실제 응답 기준일을 직접 조회한 결과는 아닙니다.

권장 순서:

1. Gold 게시 완료 버전을 고정하여 읽고 검증합니다.
2. 기존 NB_01에서 그 Gold 버전의 피처를 재계산합니다.
3. 해당 실행의 피처 버전과 기준일을 NB_10에 전달합니다.
4. NB_10, NB_11, 기존 Copy와 Promote가 같은 버전만 전달하도록 검사합니다.
5. Gold 기준일보다 피처가 오래됐으면 기존 서비스 스냅샷을 유지하되, 갱신 성공으로 처리하지 않고 지연 원인을 기록합니다.

현재 매시간 실행되는 전송 파이프라인과 모델 재학습은 별도로 운영합니다. 피처를 최신화할 때마다 모델을 다시 학습할 필요는 없습니다. 상위 Gold 게시 이벤트/실행 완료에 NB_01을 연결하거나 기존 전송 파이프라인 앞에 준비 단계를 추가할 수 있습니다. 새 노트북을 만들 필요는 없습니다.

## 반드시 보존할 로컬 계산

| 항목 | 현재 Fabric 연구 경로 | 고정한 Huber 경로 |
|---|---|---|
| 충격 기간 | 5거래일 누적 변화 | 다음 거래일의 원 관측 변화. 1일/5일 예측 모두 동일한 이 충격 입력 |
| 충격 원천 | Gold의 시작값/끝값 | 원 관측일 자료에서 거래일 이전 값 선택, 최대 나이 7일 |
| 환율 | 단순 변화율 % | 내부 로그 변화율. 서비스의 % 입력을 `100*log1p(pct/100)`로 변환 |
| 유가 | 5일 단순 변화율 % | 내부 달러 차이. 서비스의 % 입력은 기준 유가로 달러 차이 변환 |
| 상태 | 시장 피처 6개 | 종목별 `ret20_z`, `vol_ratio` |
| scale | Ridge의 vol20/60 평균 기반 sqrt5 | 원본 EWMA(alpha=.06) 변동성에 sqrt(horizon) 적용 |
| 정답 | `y_log_return_5d` | 기간별 단순수익률 %. 로그 변환은 검증된 학습 함수 내부에서 수행 |
| 구간 | CatBoost CQR 또는 Ridge 검증기간 잔차 | 과거 252개 절대오차/scale, 최소 60개, 원본 순위식 |
| 과거 평가 | 2023년 이후 기존 연구 표본 | 원본 Huber 평가 날짜를 고정. 신규 날짜의 전진 평가는 별도 |

원 관측자료는 기존 로컬 재현 파일로 과거 일치 검증을 할 수 있습니다. 향후 자동 재학습에는 같은 정의의 원 관측 시계열 갱신이 추가로 필요합니다. 현재 Gold의 as-of 상태를 차분하는 것으로 대체하면 안 됩니다. 원본의 발표 시각 가정과 실제 당시 입수 가능성 검증도 구분합니다.

공유 패키지 기준 경로는 `analytics/src/huber_pipeline/`이며 고정된 모델 계산은 PR #15의 커밋 `5a4c987b41eb2bbaeda75b45d81bd2cfc49aa2b5`입니다. 새 Fabric Environment에 필요한 의존성과 패키지를 버전 고정하여 배포하고 기존 노트북은 로드, 호출, 저장, 실행 제어를 담당하도록 구성합니다.

## 구간과 AI 응답을 바꾸지 않는 조건

원본 132,394건에서 중심값과 q05/q95를 검증합니다. 실제 AI 전달 형식으로 변환할 때도 이 값을 그대로 넘깁니다. 원본 90% 구간과 별도로 추가한 q10/q90의 80% 출력은 기존 90% 계산을 바꾸지 않습니다. 기준 성능은 [원본 구간 검증](../huber_interval_contract_20261111/README.md)에 고정돼 있습니다.

원본 검증용 `inputs.parquet`는 초기 표본 60개 미만일 때 사용했던 B147 반폭의 근거도 포함합니다. Fabric 과거 재현 단계에서 이 고정 보조자료와 해시를 패키지/데이터 저장소에 제공해야 합니다. 현재 최신 40개 모델은 모두 과거 오차 252개가 있어서 초기 대체 구간이 필요하지 않습니다.

## 웹 연결에서 함께 확인할 사항

GitHub 최신 공통 API `services/api/src/gateway.py`는 42행에서 `catboost`와 `ridge`만 허용하고, 199~200행에서 5일 로그수익률을 단순수익률로 변환하며, 215행의 기간도 5일로 고정합니다. Huber는 이미 단순수익률을 반환하므로 같은 필드에 넣고 지수 변환하면 결과가 다시 달라집니다.

기존 웹/인증/전송 구조는 유지하되, Huber를 활성화할 때 모델 종류와 기간 및 수익률 단위를 응답 계약으로 구분해야 합니다. Huber의 원본 중심값과 구간은 변환 없이 공통 응답에 전달하고, 기존 CatBoost/Ridge의 로그 변환 경로는 해당 모델에서 유지합니다. PostgreSQL의 상태 컬럼 확장과 ML 서버의 읽기 코드도 같은 릴리스에서 검증해야 합니다. Fabric만 바꾸고 현재 서버의 해석을 그대로 두면 완전한 이식이 아닙니다.

## 적용 순서

1. 현재 Fabric 원본을 GitHub `analytics/notebooks/`에 기존 이름으로 저장하고 해시를 대조합니다. 현재 해당 폴더에는 안내 파일만 있으며 성진 담당 노트북의 소스는 들어 있지 않습니다. 원본 내 인증정보 포함 여부를 검사한 뒤 커밋합니다.
2. 현재 예약 경로의 Gold → 피처 갱신 누락부터 기존 노트북/Activity 연결로 수정합니다.
3. NB_00~04에 Huber 공유 패키지와 입력 계약을 연결합니다. 별도 복제 노트북을 만들지 않고 기존 노트북 안의 모델 분기를 사용합니다.
4. NB_06~09에서 원본과 동일한 중심값, 구간, 평가 결과 및 패키지를 검사합니다. 검증 중에는 현행 서비스 게시 경로를 덮어쓰지 않습니다.
5. NB_10~11, PostgreSQL 필드와 ML API 어댑터를 같은 계약으로 맞춥니다.
6. 고정 Gold 버전에서 로컬과 Fabric의 학습 표본, 피처, 계수, 132,394개 원본 예측 및 양끝을 대조한 뒤 패키지 교체를 진행합니다. 최신 데이터는 별도 날짜 평가로 추가합니다.

기존 흐름을 유지할 수 있지만 모델 이름만 바꾸는 작업은 아닙니다. 변경의 중심은 피처/충격/학습 호출, 모델 패키지, 상태 전달 필드입니다. 이번 검토에서는 실제 수정이나 학습을 수행하지 않았습니다.
